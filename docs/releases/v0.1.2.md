# v0.1.2

这一版修的是**引擎替模型做了一个它不该做的判断**：它把提问当成任务，逼模型给一句
问话硬造产出。顺带修掉预览卡上三个用户天天撞见的毛病。

升级方式见 [docs/INSTALL.md](https://github.com/pharaoh-2727/dsh-prompt-optimizer/blob/master/docs/INSTALL.md)。
装法 A/B/C 都适用，覆盖文件后重启 DSH 即可。

---

## 提问被当成了任务

**症状**：输入一句问话（「怎么配置 profile？」），优化结果被补成一串「目标 / 步骤 / 产出格式」，
像在回答一个没人提的任务。用户拿到手的不是自己那句话的改写，是模型替它编出来的需求。

**成因**：引擎判断「要不要给输出套内容下限」用的是 `TASK_HINT` —— 一张上百词的正则表。
它把 `如何|怎么|为什么|能否|配置|插件|解释|分析` 全算任务信号，于是**所有中文疑问句都命中**
（实测 8/8）。判成任务之后，均衡档会给它套上内容下限：

```
怎么配置 profile？（13 字）→ 下限 47 字
```

而提示词自己给的正例只有 38 字 —— **照提示词写反而判不合格**。引擎于是带着
「本次输出至少 47 字」重试，模型只能编出「产出 / 验收」把字数凑够；凑够的稿子
长度合格，就被收下，还标成「已补齐」。

这是「补写之后又超长」那类事故的另一半：0.1.1 堵住了「重试后超长」，
但「重试后不超长、内容是编的」一直在线上跑。

**修法**：判据不是新发明的，是提示词里早就写好的那条（`shared-common.txt` 第 17 行）：

> 只要需要 DSH 读写文件、跑命令或查看工作区才能推进，一律算 c)；
> 只有不需要接触工作区的纯知识问答才算 b)。

所以新的 `classifyInput()` 找的是**指向工作区的字面信号** —— 路径、文件名、反引号里的命令、
报错原文、工作区名词配动作动词 —— 而不是「句子里有没有动词」。

判定顺序是这份实现的关键：

| # | 条件 | 结果 |
|---|---|---|
| 1 | 路径 / 命令 / 报错原文 | c)（哪怕写成疑问句） |
| 2 | 请求词（帮我 / 给我 / 麻烦） | c) |
| 3 | 工作区名词 + 动作动词 | c) |
| 4 | 疑问句式 | b) —— **必须排在 5 之前**：「怎么改」里的「改」是宾语 |
| 5 | 有动作动词 | c) |
| 6 | 其余 | a) |

**判不准时偏 b)**（不设下限）。这和提示词里「拿不准时按 c)」方向相反，是有意的：
模型按 c) 多写一句，用户删掉即可；引擎按 c) 会强制重试并命令模型「至少写 N 字」，
模型只能编造。代价不对称，所以默认值必须相反。

顺带删掉了均衡档的「自检」段 —— 它要求模型回看原文判断「有没有漏掉交付意图」，
模型做不到。它当时是唯一挡住编造的护栏，**判据修好后才有资格删**。

## 预览卡三个毛病

### 思考过程漏进结果框

**症状**：结果框里出现「这是 b) 类简单提问，只需改写成一句更清楚的提问」这类话 ——
模型的草稿纸躺在那里。长一点的思考还会把卡片撑成上下两坨，分不清哪一版是要用的。

**成因**：模型有 `reasoning`（思考）和 `text`（正文）两条通道，但有的模型会把推理一起塞进正文。
实测一次优化能推 **350–710 帧 reasoning**（几百到几千字），而正文只有十几到一百多字。

**修法**：

1. 正文里剥掉混进来的思考。判据很保守 —— 只认**与 reasoning 整行相同、且长度 ≥ 8 字**的行。
   提示词里出现和思考相似的词很正常，删错比留着更糟。
   剥在**状态层**（流式 `onText`、收尾 `set`、`pushHistory`），不只是渲染层：
   「复制」和「替换草稿」拿的是 `previewStore.state.result`，只剥渲染会让草稿里又带上草稿纸。
2. 思考块默认收起成一行「思考过程 · N 字」，点标题展开。它是旁注，不是结果。

### 点「放弃」之后，优化完成又自己弹回来

**成因**：放弃只把 `phase` 打回 `idle`，但 `requestId` 保持不变 ——
「还是不是当前这次」判不出「用户已经关掉了」。done 一到就无条件写 `phase:'ready'`。

**修法**：收尾时用「phase 还是不是 running」判断这次结果是否已被用户关掉。

### 预览卡跟着别的对话跑

**成因**：`previewStore` 是模块级单例，一个标签页只有一份，不记归属。
界面里却能同时开着好几个对话 —— 在 A 里点优化、切到 B，B 的输入框上方照样挂着 A 的结果。

**修法**：新增 `ownerSessionId`。卡片只显示在发起它的那个会话；切走隐藏、切回还在。
拿不到 `sessionId` 时不拦 —— 宁可显示，也不要把用户的结果藏起来。

## 兼容性

- 无破坏性改动。六个入口、配置项、`localStorage` 键名、HTTP 路由都没动
- `classifyInput()` 是**新增导出**，只为测试钉住判据；不导出也不影响运行
- 预览卡新增 `ownerSessionId` 字段，是 `previewStore` 内部状态，不进 HTTP 回执
- 宿主侧 `promptOptimizer` 服务的接口版本仍是 `version: 1`
