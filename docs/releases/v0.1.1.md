文档里的测试套数与代码行数停在改动之前。

## 这一版修了什么

### 结果会在中途"自己变成另一个结果"

**症状**：点「优化」后预览卡开始逐字出字，出到一半停住，等几秒，整段正文换成另一份。
界面上没有任何说明，看起来像出了两次结果。

**成因**：只有第一次尝试是逐字流的。之后的两次补救 —— 过度扩写拉回、档位收敛与补齐 ——
是整段换稿，它们没有把新正文推给客户端，客户端只在 `done` 事件里拿到最终结果，
于是接到的时候整段替换。

**修法**：补救开工前先推一条 `revise` 事件说明原因，收尾再补推一帧最终正文。两条合起来
保证一件事：

> 界面收到的**最后一帧 `delta` 永远等于 `done.text`**，客户端不会在 `done` 里凭空空降一份新结果。

`revise` 的形状是 `{reason, text}`：`reason` 取 `trimmed` / `expanded` / `recovered`，
`text` 是一句给人看的话。客户端把它显示在预览卡标题行，替代原来的"生成中…"。

| 补救类型 | 标题行显示 |
|---|---|
| 超出档位上限，重新收敛 | 超出这一档的长度上限，正在重新收敛… |
| 不足档位下限，补写 | 这一档要求补出产出与验收，正在补齐… |
| 短输入被扩成文档，改用精简档 | 内容超出输入的长度，改用精简档重写… |

### 其余三条修复

- **上一批事件迟到时不再覆盖新一次优化** —— 客户端按 `requestId` 认领事件，
  旧请求的 `delta` 落到新请求上会被丢弃
- **正在生成时点「优化」会真的再开一次**，而不是被静默忽略
- **回执里的 provider / model 取自真正产出这份正文的那一轮** —— 补救可能换过路由，
  以前报的是第一轮的路由

## 测试

新增 `dev/test-result-stability.cjs`，钉住上面那条不变量。两个用例：

| 用例 | 断言 |
|---|---|
| I1 末次 `delta` 等于 `done.text` | 界面最后收到的那一帧就是最终正文 |
| I2 正文与流下来的不同时，流里必先有 `revise` 且带 `reason` | 换稿必须看得见 |

`dev/test-preview-flow.cjs` 补三条断言：换稿说明显示在卡上并在结束后消失、
上一批迟到事件不覆盖新结果、点别处收起历史浮层。

```bash
npm test    # 9 套，约 5 秒，不需要 DSH 在跑
```

## 兼容性

- 无破坏性改动。六个入口、配置项、`localStorage` 键名、HTTP 路由都没动
- `revise` 是**新增**事件。旧客户端不认识它会忽略掉，行为回到 0.1.0（结果照样对，
  只是不会显示换稿原因）。反过来，新客户端连老宿主也不会出问题：没有 `revise` 时标题行
  保持「生成中…」
- 宿主侧 `promptOptimizer` 服务的接口版本仍是 `version: 1`

## 校验

- `npm run check` 通过
- `npm test` 9 套全绿（本机 5.3s）
- CI 在 ubuntu 的 Node 20 / 22 上跑同一套
